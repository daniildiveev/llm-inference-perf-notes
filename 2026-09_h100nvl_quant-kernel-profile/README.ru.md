# FP8 norm+quant fusion в vLLM на H100: регрессия из-за выбора GEMM и медленный фьюженный кернел

Расследование стоимости квантизации активаций на FP8 block-scaled decode-пути vLLM. Началось с вопроса «почему не срабатывают fusion-пассы», закончилось двумя находками: принудительный фьюжн norm+quant на sm90 даёт чистый проигрыш из-за того, какой GEMM-бэкенд запускается после него, а фьюженный кернел `rms_norm_per_block_quant` медленный и сам по себе.

**Окружение.** Qwen3-8B-FP8 (W8A8, блочные скейлы 1×128), H100 NVL (132 SM, пик HBM3 3,9 ТБ/с), непривилегированный контейнер vast.ai. Сборки: end-to-end прогоны при bs=1 — на vLLM 0.23.1rc1.dev1458 (nightly), прогоны при bs=256 и все микробенчи — на vLLM 0.23.0 (PyPI). Внутри каждой колонки каждой таблицы все армы сняты на одной сборке. Числа на уровне кернелов сняты до vLLM #54111 (см. [Что произошло в апстриме](#что-произошло-в-апстриме-за-время-работы)).

## TL;DR

- **Принудительный фьюжн norm+quant сегодня даёт чистый проигрыш:** +13% к латентности decode при bs=1 (предсказание по трейсу подтверждено wall clock) и +56% GPU-времени на decode-шаг при bs=256 (по трейсу; wall clock не снят). Выбор GEMM даёт ~1970 из ~2700 мкс/шаг разрыва при bs=256; quant-кернел — ~160.
- **Фьюженный кернел медленный сам по себе:** `rms_norm_per_block_quant` гоняет меньше памяти, чем заменяемая им пара rms_norm + quant, но в изоляции медленнее в 1,08–1,36 раза. Его предельная стоимость на элемент ~5,5× от стоимости пары, и он достигает 17–34% пика HBM3.

| Decode-шаг, Qwen3-8B-FP8, H100 NVL | bs=1 | bs=256 |
|---|---|---|
| A: без фьюжна, дефолтный бэкенд | база | 4782 мкс |
| B: norm+quant фьюжн, DeepGEMM | ≈ +13% | — |
| C: norm+quant фьюжн, CUTLASS blockwise | ≈ +13% | 7478 мкс (+56%) |

Дельты при bs=1 — end-to-end латентность; значения при bs=256 — суммарное GPU-время кернелов на decode-шаг по трейсу.

## 1. На sm90 фьюжн сегодня в минусе

**Почему пассы не срабатывают.** Дефолтный linear-бэкенд на sm90, `FlashInferFp8DeepGEMMDynamicBlockScaledKernel`, принимает BF16-активации и квантует их внутри, через `scale_1x128_kernel` из TRT-LLM. `RMSNormQuantFusionPass` матчит собственный quant-оп vLLM, поэтому фьюзить ему нечего, хотя в логах пасс значится включённым. Это согласуется со skip'ами в `tests/compile/fusions_e2e/test_tp1_quant.py`.

**Сколько стоит принудительный фьюжн.** Армы B и C отключают дефолтный бэкенд через `VLLM_DISABLED_KERNELS`. Linear тогда откатывается на бэкенды, принимающие уже квантованный вход, и существующий fusion-пасс срабатывает.

- **bs=1, A→C:** +548 мкс на шаг. Из них +362 мкс даёт GEMM (потеря пути `deep_gemm::fp8_gemm_kernel_swapAB`) и +186 мкс — фьюженный norm+quant кернел, который делает на 108 запусков меньше, но тратит больше времени. В этом прогоне регрессия, предсказанная по трейсу (+11,1 мс), сошлась с регрессией по wall clock (+12,2 мс).
- **bs=256:** `cutlass_3x_gemm_fp8_blockwise` тратит 33,6 мкс/запуск против 19,9 мкс у `deep_gemm::fp8_gemm_kernel_swapAB` (1,69×). Это ≈1972 мкс на шаг (≈26% шага арма C), тогда как quant-кернел — ≈163 мкс (2,2%). Разрыв по GEMM растёт с батчем: +362 мкс/шаг при bs=1, ≈1972 мкс/шаг при bs=256.

**Почему это важно.** По роадмапу на Q3 vLLM переносит quant fusion из `torch.compile`-пассов в код модели через `QuantizedActivation` (RFC #42770, #43224; порт RMSNorm+quant отслеживается в #43500). Как только norm начнёт выдавать уже квантованные активации, linear не сможет использовать дефолтный бэкенд sm90, если тот не научится принимать внешнюю квантизацию. Без этого порт унаследует регрессию выше. Два выхода: включать фьюженный norm+quant на sm90 в зависимости от выбранного linear-бэкенда или научить дефолтный бэкенд принимать квантованный вход, чтобы фьюжн убирал шаг квантизации, не жертвуя GEMM.

## 2. Фьюженный кернел медленный сам по себе

| кернел | нс / элемент (свип по hidden, n=1) | полоса HBM3 (n=16384, пик 3,9 ТБ/с) |
|---|---|---|
| `rms_norm` отдельно | 0.105 | 81–89% |
| блочный quant отдельно | ~0.005 | 32% |
| **сумма частей** | **0.110** | — |
| отдельная пара, измерено | — | 49–58% |
| **фьюженный** | **0.609** | **17–34%** |

- **Общее время в изоляции.** На той же работе фьюженный кернел медленнее отдельной пары в 1,08–1,36 раза. При n=16384 без residual он гоняет 43% байт пары за 128% её времени; с residual соотношение 1,09×.
- **Нижняя граница при n=1.** На пустом GPU нижняя граница фьюженного кернела — 5,5 мкс против 4,4 мкс у отдельной пары (2,2 + 2,2). Оба здесь работают одним блоком, так что занятость SM объяснением не является.
- **Модель стоимости** для продакшновой формы (hidden=4096, group=128), подогнанная по свипу hidden при n=1: 5,70 мкс = 2,40 мкс фиксированных (42%) + 0,609 нс/элемент (44%) + 25,3 нс/группу (14%). Изолированная нижняя граница (5,5 мкс) и подгонка (5,70 мкс) взяты из разных свипов. Среднее внутри модели по трейсу bs=1 (6,85 мкс/запуск) определяется вариантом с residual в условиях реальной модели.
- **Потолок по полосе.** Без residual при n=16384 кернел гоняет 203 МБ. При достижимых ~3,3 ТБ/с это ~62 мкс; измерено 314 мкс, то есть примерно в 5 раз хуже.
- **Сравнение в продакшне, с оговоркой.** Внутри модели фьюженный кернел тратит 6,85 мкс/запуск при bs=1 и 7,08 при bs=256 против 4,04 и 4,82 у пути без фьюжна (1,70× и 1,47×). Эта база — `scale_1x128_kernel` из TRT-LLM плюс Triton-норма от Inductor, а не собственная пара vLLM, так что часть разрыва — это «quant-кернел TRT-LLM быстрее, чем у vLLM», а не «фьюжн медленный». Сопоставимое число — изолированные 1,08–1,36× выше.

**Отсеяно:**
- **Занятость SM.** Время на запуск плоское при росте батча в 256 раз (6,85 → 7,08 мкс), и кернел проигрывает при n=1 на пустом GPU.
- **Транспонированная запись скейлов.** `transpose_scale` True против False — 3–8% везде.
- **Последовательные групповые редукции.** Реальны, но это 14% стоимости; изолированы контролем по `group_size`.

**Вероятные причины** (из чтения кернела на `main`, ещё не подтверждено через `ncu` или SASS):
- три отдельных grid-stride прохода по строке, каждый перечитывает input (и residual, если он есть);
- 8-байтные векторные загрузки для bf16 (`VEC_SIZE=4`) там, где доступны 16-байтные;
- нет `__launch_bounds__`.

## Что произошло в апстриме за время работы

- **vLLM #54111** (мёрдж 27.08.2026) переписал `compute_dynamic_per_token_scales` (фикс гонки). Замеры здесь сняты до него, поэтому per-group компонент (14%) надо перемерить на HEAD. Три прохода и vec4-загрузки не тронуты.
- **vLLM #36895** добавляет опциональную реализацию `rms_norm_per_block_quant` на Helion, которая по заявлению в 1,67–2,06 раза быстрее C++-кернела на H100. C++-кернел остаётся дефолтным. Это независимое подтверждение того, что C++-кернел недобирает производительность.
- **flashinfer #4480** (мёрдж 26.08.2026) — `FusedAddRMSNormFP8BlockQuant`: один проход, ~75% пика HBM на H200, скейлы пишутся в той раскладке, которую потребляет DeepGEMM.

## Известные пробелы

- Wall clock при bs=256 не снят; числа для bs=256 — GPU-время, выведенное из трейса.
- Нет `ncu`: в непривилегированном контейнере он падает с `ERR_NVGPUCTRPERM`. Цифры по полосе выведены из объёма переданных байт и измеренного времени.
- Сырые трейсы профайлера не сохранились (лежали в `/dev/shm` на GPU-хосте). `run_bs256.sh` генерирует их заново.
- Измерен только sm90 (H100 NVL). Другие архитектуры не проверены.
- Запланирован перезапуск на свежем nightly, чтобы покрыть #54111 и снять wall clock при bs=256.

**Оговорки по инструментам.** Маркер в `an2.py` может совпасть с ArgMax `reduce_kernel`, который срабатывает примерно дважды за шаг, и тогда получаются сегменты по полшага. Окна проверены переписью кернелов по 36-слойной модели: 568 запусков на шаг при bs=1 (арм A), 1120 при bs=256 (арм C). Категории кернелов определяются регэкспами, а `scale_1x128_kernel` живёт в неймспейсе `fp8_blockscale_gemm`, поэтому матчить его надо явно по `scale_1x128`.

## Воспроизведение

```bash
# Арм A (дефолт). Для B и C добавить префикс:
#   B: VLLM_DISABLED_KERNELS=FlashInferFp8DeepGEMMDynamicBlockScaledKernel
#   C: VLLM_DISABLED_KERNELS=FlashInferFp8DeepGEMMDynamicBlockScaledKernel,DeepGemmFp8BlockScaledMMKernel
vllm bench latency --model Qwen/Qwen3-8B-FP8 \
  --input-len 1024 --output-len 16 --batch-size 1 \
  --num-iters-warmup 1 --num-iters 1 --profile \
  --profiler-config.profiler=torch \
  --profiler-config.torch_profiler_with_stack=false \
  --profiler-config.torch_profiler_dir=./traces/A

# bs=256, армы C и A. Написано для H100-контейнера на vast.ai: ставит vLLM 0.23.0
# в /root/venv, ожидает an.py и an2.py в /root, пишет /root/RESULTS256.txt
cp an.py an2.py /root/ && bash run_bs256.sh

# Перепись кернелов на шаг по трейсу
python an2.py <trace.json.gz>

# Микробенчи (нужна сборка vLLM с _C-опами; числа выше — с H100 NVL)
python microbench_quant.py
python microbench_hidden.py
```

**Заметки по окружению** (контейнер vast.ai; подробности в `run_bs256.sh`):
- `/dev/shm` — tmpfs, смонтированный с `noexec`, поэтому venv должен жить на overlay: `.so` из torch не `dlopen`'ятся из tmpfs.
- `uv` распаковывает колёса в `TMPDIR` перед переносом в venv. На overlay в 16 ГБ это удваивает объём каждого пакета и упирается в `ENOSPC` на torch, поэтому `TMPDIR` указывает на `/dev/shm`.
- Inductor и Triton JIT-компилируют свои лаунчеры и `dlopen`'ят их, поэтому `TORCHINDUCTOR_CACHE_DIR` и `TRITON_CACHE_DIR` должны указывать на overlay с правом исполнения, а не на `TMPDIR`.
- Nightly-колесо, использованное для bs=1, позже стало отдавать 404, поэтому всё остальное запинено на vLLM 0.23.0 из PyPI.
- `ncu` нужны права на счётчики производительности GPU, которых у непривилегированных контейнеров нет.
