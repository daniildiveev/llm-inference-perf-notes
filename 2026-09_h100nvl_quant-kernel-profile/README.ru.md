# vLLM FP8 quant fusion: `rms_norm_per_block_quant` упирается в память на 17–34% пика

Расследование стоимости квантизации активаций на FP8 block-scaled decode-пути vLLM (Qwen3-8B-FP8, H100 NVL). Началось с вопроса «почему не срабатывают fusion-пассы», закончилось измеренным утверждением об одном кернеле, не зависящим от бэкенда, — плюс более крупной находкой по GEMM, отложенной на потом.
Скрипты и сырые свипы — в этом репо; всё воспроизводится одними CUDA events, без `ncu`, а микробенчи работают на потребительской карте.

## Утверждение

`vllm::rms_norm_per_block_quant_kernel` обходит строку примерно в 5,5 раза медленнее, чем два кернела, которые он заменяет, делая ровно их работу:

| кернел | нс / элемент | полоса HBM3 (n=16384) |
|---|---|---|
| `rms_norm` отдельно | 0.105 | 81–89% |
| блочный quant отдельно | ~0.005 | 32% |
| **сумма частей** | **0.110** | — |
| **фьюженный** | **0.609** | **17–34%** |

При n=1, один блок, пустой GPU: фьюженный — 5,5 мкс против 2,2 у сопоставимого одиночного кернела. Занятость SM объяснением не является.

Модель стоимости для продакшновой формы (hidden=4096, group=128), 5,70 мкс всего: 2,40 фиксированное (42%) + 0,609 нс/элемент (44%) + 25,3 нс/группу (14%). Потолок только по полосе: 203 МБ при 3,3 ТБ/с — ~62 мкс вместо 314, то есть ~5×.

Вероятная причина (из чтения кернела на `main`): три отдельных grid-stride прохода по строке, каждый перечитывает input; 8-байтные векторные загрузки для bf16 (`VEC_SIZE=4`) там, где доступны 16-байтные; нет `__launch_bounds__`. Это переводит находку из «issue с измерением» в «PR с диффом».

## Как установлено

1. **Профилировка** decode-шага Qwen3-8B-FP8 на H100: 568 запусков кернелов на шаг, 144 из них (25,4%) — квантизация активаций (`scale_1x128_kernel`, TRT-LLM), ~6% времени шага. Границы шага найдены двумя независимыми способами (автокорреляция имён кернелов + сегментация по маркеру сэмплера), перепроверены переписью кернелов по 36-слойной модели.
2. **Гипотеза 1** — пассы сломаны, на столе ~6% — **опровергнута собственным A/B/C-экспериментом** через `VLLM_DISABLED_KERNELS`: пассы исправны, они просто не видят внутрь C++ TRT-LLM; принудительный фьюжн стоит ~13% end-to-end. Регрессия, предсказанная по трейсу (+11,1 мс), сошлась с wall clock (+12,2 мс).
3. **Декомпозиция** регрессии: две трети — потеря M=1-специализации `swapAB` в DeepGEMM, треть — сам фьюженный кернел, который делает на 108 запусков меньше и тратит на 186 мкс больше.
4. **Три ложных объяснения отсеяны** — занятость SM (плоско на 256× по батчу и проигрывает при n=1 на пустом GPU), транспонированная запись скейлов (3–8% везде), последовательные групповые редукции (реальны, но 14% стоимости; изолированы контролем по `group_size`).
5. **Микробенч-свипы** по числу токенов, hidden и group_size → разложение на per-element, per-group и фиксированную стоимость.

## Почему это важно

По квартальному роадмапу vLLM переносит quant fusion из `torch.compile`-пассов в явный фьюжн в коде модели через `QuantizedActivation` (RFC #42770, #43224). Всё, что сегодня идёт через pattern matcher, пойдёт через кернелы этого типа. Медленный фьюженный кернел — препятствие их собственному плану, а не придирка к побочному пути.

## Что произошло в апстриме за время работы

- **vLLM #54111** (мёрдж 27.08.2026) переписал `compute_dynamic_per_token_scales` (фикс гонки). Замеры здесь сняты до него; per-group компонент (14%) надо перемерить на HEAD. Три прохода и vec4-загрузки не тронуты.
- **flashinfer #4480** (мёрдж 26.08.2026) — `FusedAddRMSNormFP8BlockQuant`: один проход, ~75% пика HBM. Фьюженный кернел в апстриме теперь есть; оставшийся разрыв — на стороне vLLM.

## Более крупный приз, отложенный в сторону

`cutlass_3x_gemm_fp8_blockwise` против `deep_gemm::fp8_gemm_kernel_swapAB`: 33,6 против 19,9 мкс/запуск (1,69×), разрыв **растёт** с батчем — ≈1972 мкс/шаг при bs=256, в 12 раз больше quant-кернела. Является ли этот путь дефолтным на sm89 (Ada) — не проверено, и это определяет вес обеих находок.

## Воспроизведение

```bash
vllm bench latency --model Qwen/Qwen3-8B-FP8 --input-len 1024 --output-len 16 --batch-size 1 \
  --profile --profiler-config.profiler=torch --profiler-config.torch_profiler_dir=./traces/bs1
# армы: VLLM_DISABLED_KERNELS=FlashInferFp8DeepGEMMDynamicBlockScaledKernel[,DeepGemmFp8BlockScaledMMKernel]
python microbench_hidden.py   # свип по hidden при n=1
python microbench_quant.py    # отдельный quant-кернел
```

Заметки по окружению (noexec `/dev/shm`, пиннинг nightly-колеса, пик диска у `uv`, флаги профайлера, отсутствие `ncu` в непривилегированном контейнере) — в отчёте.
